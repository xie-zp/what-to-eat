# 过敏原约束有效性实验

对比"仅在提示词里声明过敏原"与"把过敏原作为硬约束传入检索"两种做法，统计返回结果中仍包含过敏原的比例。

## 实验设计

- **查询组合**：5 个过敏原（花生、虾、鸡蛋、牛奶、猪肉）× 4 种通用推荐问法 = 20 组
- **问法特点**：都是"推荐几道家常菜"这类中性表达，**不含任何排除语义**，用于检验系统是否会主动执行用户声明的过敏原约束
- **违规判定**：独立检查返回菜谱的食材列表，不依赖任何校验代码
- **复现**：`python scripts/evaluate_safety.py`

## 实验结果

| 配置 | 违规推荐数 | 违规率 | 无结果查询数 |
|---|---:|---:|---:|
| 仅提示词声明（无硬过滤） | 10 / 100 | **10.0%** | 0 / 20 |
| 过敏原作为硬约束（本方案） | 0 / 100 | **0.0%** | 0 / 20 |

## 结论

1. **仅靠提示词无法保证安全**：在完全中性的推荐问法下，未施加硬过滤的方案仍有 10% 的返回结果包含用户已声明的过敏原。这类违规在真实场景中可能造成健康风险。
2. **硬约束把违规率降到 0**：过敏原在工具参数层直接参与候选过滤，不依赖模型是否"记得"约束。
3. **过滤没有牺牲可用性**：两种配置的无结果查询数都是 0/20，说明排除过敏原后仍能给出足量候选，不存在"过度过滤导致拒答"的问题。
4. **设计含义**：安全类约束必须实现为**代码可执行的条件**，而不是提示词里的一句话。这也是项目把过敏原、忌口、时间、难度统一放在 `exclude_ingredients` 与校验节点双重执行的原因。
