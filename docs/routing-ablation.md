# 查询路由增益实验

对比"固定单策略"与"按查询复杂度自动路由"在同一批查询上的表现。

## 实验设计

- **查询集**：33 条常规查询 + 8 条复杂查询（多条件、关系型、因果解释），共 41 条
- **标准答案**：独立按菜谱字段推导
- **复现**：`python scripts/evaluate_routing.py`

## 实验结果

| 配置 | Precision@5 | 平均延迟 |
|---|---:|---:|
| 固定混合检索（向量 + BM25） | 0.756 | 340 ms |
| 固定混合 + 图谱（全通道） | **0.800** | 345 ms |
| 按策略路由（本方案） | 0.766 | 332 ms |

路由决策分布：`hybrid_traditional` 37 条、`graph_rag` 3 条、`combined` 1 条。

## 结论（含对方案不利的发现）

1. **路由机制本身工作正常**：简单查询走轻量通道、复杂查询（"只有鸡肉和蔬菜""豆腐替代肉类""为什么川菜用花椒而不是胡椒"）正确升级到图谱检索。
2. **但在本项目规模下，"始终启用图谱"的精度更高**（0.800 vs 0.766）。原因是路由把大多数查询留在不带图谱的轻量通道，而其中一部分其实能从图谱召回中受益。
3. **路由的延迟收益也不明显**（332 ms vs 345 ms，仅 13 ms）。因为图谱通道是精确匹配、平均只需 9 ms，仅占整体延迟的 2.6%（其余主要是 BGE 向量编码）。
4. **由此得到的工程结论**：在中小规模知识图谱（数千节点）场景下，**"全通道召回 + RRF 权重调优"比"按查询复杂度做通道裁剪"更简单且效果更好**；查询路由更适合图谱规模大、单次图查询代价高的场景。

## 对方案表述的影响

- **不应主张**"查询路由提升了检索精度"——在本地实验中它低于全通道策略。
- 可以主张的是：路由机制已实现并在复杂查询上正确分流，同时通过实验确认了它在当前数据规模下的收益边界。
- 若后续图谱规模增长到十万节点量级，路由的成本收益会反转——这正是保留该模块的理由。
