# 三分钟项目介绍

## 一句话

Recipe Agent 是一个基于 LangGraph、Neo4j 和 Milvus 的食谱规划 Agent，能够理解用户约束，检索菜谱，规划多日菜单，生成购物清单，并使用长期记忆保护过敏原等硬约束。

## 为什么做

普通菜谱问答存在三个问题：

1. 模型可能编造不存在的食材或步骤
2. 只支持单轮问答，不能完成多步骤任务
3. 不能可靠处理过敏原、库存、时间和营养约束

本项目将 RAG 作为 Agent 的知识工具，而不是把整个系统限制在检索问答中。

## 系统组成

### 数据层

- HowToCook Markdown 菜谱解析
- 322 道标准化菜谱
- 104 道菜谱从原文提取明确制作时间，其余保留为“时间未标注”
- 4,382 个知识图谱节点
- 7,162 条图谱关系

### 检索层

- Neo4j 菜谱和关系查询
- 食材类别与多跳搭配推理
- BGE 向量化
- Milvus 向量检索
- BM25 关键词检索
- RRF 融合

### Agent 层

- LangGraph 状态图
- Rule-based 与 LLM Planner
- 工具注册表
- 多步骤执行循环
- 硬约束校验
- SQLite Checkpointer
- OpenTelemetry 全链路追踪

### 应用层

- FastAPI
- 响应式 Web 前端与多轮对话
- SQLite 用户画像
- Docker Compose

## 核心流程

```text
用户目标与约束
  -> 合并长期用户画像
  -> Planner 选择工具
  -> 执行菜谱检索
  -> 校验过敏原和时间
  -> 生成多日菜单
  -> 生成购物清单
  -> 返回结果和菜谱来源
```

## 技术难点

### 1. 防止模型编造食材

回答只使用工具返回的菜谱证据，并为工具结果保留菜谱 ID 和来源。

### 2. 约束不能只靠提示词

过敏原、时间和难度在程序侧强制覆盖和校验。模型不能通过提示词删除这些限制。

### 3. 多步骤循环可能失控

Planner 会阻止重复调用相同工具，并设置最大执行步数。

### 4. 教程数据不能直接作为最终数据

系统直接从 HowToCook Markdown 重新解析，形成独立的数据管道和图谱结构。

## 当前结果

- 112 个自动化测试
- 54 个真实菜谱评测场景
- Neo4j、Hybrid Retrieval 和 LLM Planner 三套评测报告
- 任务成功率、检索命中率、约束满足率和引用覆盖率均为 100%
- 35 条真实 HTTP 可靠性场景全部通过
- Neo4j、Milvus 和 Agent 均使用独立 Docker 环境
